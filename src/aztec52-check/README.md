# Aztec 5.2a compatibility investigation — 2026-11-01

**Conclusion: a viable separate toolchain, not yet a drop-in replacement.**
The ordinary calling/object interfaces tested are compatible with the patched
4.2 runtime. Floating constants and runtime source compatibility need attention
before adopting 5.2. No installed tools, headers or libraries were changed by
this investigation.

## Configuration and results

The candidate is the museum's [Aztec 5.2a distribution](https://www.aztecmuseum.ca/az8652a.zip):
CC 5.2a 1992-11-17, CGEN 5.2a 1992-10-26, assembler 5.2a 1992-10-06.
Archive SHA-256:
`456b6da476629bef8ef8396d2f093b1f459edde798910ce7dcb195c0836d1fb9`.

Application tests used the 5.2 compiler/code generator/assembler, our **4.2
headers**, the existing 4.10d linker, and the installed patched 4.2 libraries
and matching startup objects. Targets: CP/M-86, DOS 1.1, DOS 2 small/lc/ld/l.
Execution was under the existing emulators, not hardware or PCE in this study.

| Check | Result |
| --- | --- |
| Unmodified general runtime regression | Fails at HUGE_VAL equality on all six targets |
| Same regression with an investigation-only exact overflow sentinel | Passes all six |
| Infinity arithmetic/classification regression | Passes all six |
| DOS truncate regression | Passes all five DOS targets |
| Cross-compiler calls: new caller / old provider and reverse | All 12 combinations pass |
| CP/M expr, unmodified sources with REQUIRE_INFINITY | 11,298/11,298; 36 infinity checks, no skips |
| 5.2-generated sample assembly assembled with the 4.2 assembler | Links and executes successfully on CP/M |
| Rebuild small-model runtime with 5.2 | One source declaration correction required; then CP/M, DOS 1.1 and DOS 2 pass unmodified general/infinity/truncate tests where applicable |

Cross-compiler probes cover structures passed/returned by value, packed
structure sizes, data/function pointers, callbacks, varargs, float/double
arguments, long arithmetic and return values. These are probes, not exhaustive
ABI certification. Large-data and large-code application calls were tested;
the runtime rebuild experiment itself covered small models only.

The arithmetic comparison ABI remains ordered: NaN == NaN is still true,
and raw C comparisons with NaN remain unsuitable. 5.2 does not solve this
compiler/runtime convention simply by replacing the compiler.

## Confirmed numeric incompatibility

Our current header defines `HUGE_VAL` as `1.79e+308`. Its emitted binary64 bits:

| Producer | Bits |
| --- | --- |
| 4.2 compiler / installed strtod overflow return | `7fefdcf158adbb99` |
| 5.2 compiler | `7fefdcf158adbb91` |

Consequently, a 5.2 caller's `strtod(overflow) == HUGE_VAL` is false even though
errno is ERANGE and the input is consumed correctly. The diagnostic `regfix.c`
generated by the checker substitutes the precise **existing** runtime sentinel
using four integer words. It does not remove any assertions or change installed
headers. All six general regressions then pass.

Rebuilding both the caller and C math routines with 5.2 makes this particular
comparison consistent again, but does not establish correctly rounded decimal
conversion or compatibility with remaining 4.2 objects.

Additional emitted constant samples (read directly from static data):

| Literal | 4.2 | 5.2 |
| --- | --- | --- |
| `0.1` | `3fb999999999999a` | `3fb999999999999a` |
| `1e-300` | `01a56e1fc2f8f359` | `01a56e1fc2f8f35d` |
| `1e300` | `7e37e43c8800759b` | `7e37e43c88007597` |
| `1.7976931348623157e308` | `7feffffffffffffe` | `7feffffffffffff6` |
| Current `DBL_MAX` spelling | `7ff0000000000000` | `7feffffffffffff7` |
| Current `DBL_MIN` spelling | `0010000000000000` | `0010000000000004` |

The existing DBL_MAX spelling (`1.797693134862316e+308`) is itself too large:
it becomes infinity with 4.2. This is a pre-existing header issue exposed by
the comparison, not caused by the new compiler. A migration should establish
exact bit patterns for public binary limits/sentinels and test boundary
arithmetic rather than rely on decimal spellings producing identical bits.
No general accuracy advantage for 5.2 has been established.

## Runtime rebuild experiment

A private copy of the runtime was compiled using 5.2 for its C sources, the
4.2 assembler for handwritten assembly, and the existing librarian/order tools.
The first failure was `src/math/atan.c:18`:

```
double f, frexp();
```

5.2 rejects that block-scope K&R declaration after the prototype in math.h.
Removing only the redundant `frexp()` declaration in the temporary copy lets
small-model DOS C/math, CP/M C and DOS 1.1 C builds complete. Programs compiled
with 5.2 and linked with those new libraries pass the unmodified general,
infinity and applicable truncate regressions. Mixed-model rebuilds, graphics,
screen libraries, 8087 execution and application clean builds were not tested
against that rebuilt runtime. This correction is not installed.

## Integration rules and recommendation

1. Add a separately named 5.2 toolchain; retain the proven 4.2 toolchain.
2. Keep headers tied to the **runtime**, not the compiler executable. Native
   5.2 stdio.h uses `_iob`, different FILE flags/layout and different text/binary
   behavior. Its time API uses epoch seconds; our runtime retains packed DOS
   time. Native 5.2 headers/startups are not interchangeable with our libraries.
3. Resolve numeric limits/sentinels and the redundant declaration before a full
   5.2 runtime rebuild. Recheck mixed old/new objects after those changes.
4. Then run all runtime models, expr, and the seven application clean builds.
   Until that proof point, do not switch the default wrappers or fetch sequence.

The existing `src/fetch/cross_aztec52_upgrade` copies tools directly over the
4.2 installation. It was deliberately **not used**; it is unsuitable for a
side-by-side trial. The downloaded native 5.2 release is DOS-oriented; CP/M
and DOS 1.1 success here comes from retaining our target-specific runtime and
startup, not from native 5.2 CP/M/DOS 1.1 libraries.

Useful 5.2 features documented in its bundled `doc/readme.txt` include automatic
aggregate initialization, trigraph support, prototype/preprocessing options,
and explicit segment placement. Segmentation extensions, huge-pointer behavior,
profiling/debugger compatibility and ROM configurations remain untested here.

## Reproduce the installed-runtime checks

```
python3 src/aztec52-check/check.py /path/to/az8652a.zip /path/to/new-work-directory
```

The destination must not exist. Tools, temporary files and logs stay there.
`results.json` records each outcome. Raw general-regression failures are
expected until the sentinel discrepancy is resolved; `regfix` is explicitly
an investigation-only adaptation. Limits/constants entries capture observations,
not numeric-accuracy assertions. If the sibling expr checkout is present, its
complete smoke suite is also run.

For DOS 1.1 truncation, set `AZ52_DOS_EMULATOR` to an emu2 with the zero-count
FCB write correction (the fixture in `src/aztecreg/emu2-truncate.patch`). The
unfixed emulator's failure must not be mistaken for a compiler incompatibility.
The general checker does not rebuild the runtime or replace installed tools.
